# tokio-moq のトランスポート境界

## WebTransport over HTTP/2 の受信ストリーム数

受信バイト数のクレジットと受信ストリーム数のクレジットは別々に管理する。`WT_MAX_DATA` と `WT_MAX_STREAM_DATA` はアプリケーション側の消費量に応じて更新するが、現行実装は `WT_MAX_STREAMS` を補充しない。したがって、ピアが開始できる単方向ストリームと双方向ストリームは、接続時に広告する各 100 本がセッション通算の上限になる。

[draft-ietf-webtrans-http2-16 §6.7](../refs/webtrans/draft-ietf-webtrans-http2-16.txt#L1151) の `WT_MAX_STREAMS` は累積値であり、通常はストリームが終了するたびに補充できる。ただし、現在使用している `shiguredo_http2` 2026.1.0-canary.17 は、終了済みストリームの記録を上限付きで保持し、その記録から外れた古い ID を新しいストリームの暗黙的な開設時に再生成し得る。依存側が以前に開いた ID を再生成しないようにしてから、アプリケーションが受信ハンドルを解放したストリームの分だけ補充する。双方向ストリームでは、さらに両方向の終端を待つ必要がある。
